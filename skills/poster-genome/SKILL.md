# Poster Genome · Reference-First 创作

**目标：学习用户真正喜欢的作品，并让这些真实视觉参考参与下一次创作。**

设计基因（genome）是可迁移的设计决策；用户私有的 Taste Library 是可以重新打开、观察并用于图像创作的参考海报。**不能用基因的文字描述代替真实参考图。** 两者必须一起发挥作用。

这是给 Agent 的行为指令，而不是自带生图模型的软件。所有相对脚本路径都以本 SKILL.md 所在的技能目录为起点。安装后的用户资料存放在运行机器的 ~/.poster-genome，**不存放在技能文件夹或公共 GitHub 仓库**。

## 一、先识别用户模式

| 用户在说什么 | 模式 | 应交付什么 |
| --- | --- | --- |
| “学习这张海报”“为什么好看” | **LEARN** | 可见证据、设计推断、可迁移规则、适用与反例 |
| “喜欢这张，保存到我的风格库” | **LEARN → LIBRARY** | 先看图提炼喜欢/不喜欢的细节，再保存**真实图片 + 偏好记录**到用户本地 |
| “用这些照片按我喜欢的风格制作” | **CREATE** | 检索相关参考原图、真正附加图片、创作和核对 |
| “这版排版太死板”“别改变人物” | **REFINE** | 对比参考图、准确指出缺陷，并保留用户素材定向修改 |
| “整理/删除/给参考图打分” | **LIBRARY** | 只在用户明确授权下改动本地图库或公开基因 |

如果用户已经提供图片、用途和文案，不要重复提问。每轮最多问三个确实会影响创作的问题；允许用户说“其他你决定”。

## 二、最高优先级的约束

1. **真实视觉参考优先。** 对于创作，优先检索私人图库中的 1–3 张真实图片。只有元数据或基因 JSON 不足以声称“参考驱动”创作。
2. **明确两种图的角色。** 用户上传的内容图负责主体的身份、数量、服装、物品、品牌和事实；喜欢的海报是风格参考，只负责字体、色彩、版式节奏和氛围。不能把它们混作一张图。
3. **真的传入图片。** 路径字符串、Prompt 和摘要不会自动把图片送到图像模型。必须通过宿主实际支持的图像读取/附加接口传递文件内容；不支持时如实说明，不能假装已引用图像。
4. **保真先于好看。** 保留用户指定的人脸、宠物、商品、准确文字和数量；不得漏掉其中一个宝宝，或编造日期、天气、相机参数、署名、优惠和背书。
5. **学习方法，不复制作品。** 不重建第三方作品的整套独特布局、商标和原始文案，不能擅自使用未授权素材。
6. **本地保存必须授权。** 用户上传参考海报给你看，不等于允许永久保存。只有用户明确要求“加入风格库/保存参考”或同意后，才在运行环境本地写入。未经同意不得上传 GitHub、云盘或其他服务器。
7. **区分观察、推断、未知。** 视觉效果解释不等于设计师本人意图；无法确认的具体字体、原创作者、参数和权利不能硬猜。
8. **工具能力必须诚实。** 没有视觉工具不能说看过图，没有图像生成工具不能声称完成图像；没有访问本地文件的能力不能说已读取或保存用户电脑里的图库。

## 三、LEARN：学到可执行的审美判断

按 [海报分析方法](references/analysis-framework.md) 拆解。顺序为：

1. 观察图像类型、主题、画幅、主体数量、背景、图形、文案、品牌信息，标明哪些看不清。
2. 按第一眼、第二眼、最后一眼还原观看顺序；分析构图、比例、字体对比、留白、图层、色彩及装饰的作用。
3. 每条结论写清楚“画面证据 → 可能的视觉作用 → 可迁移规则 → 适用条件 → 失效条件”，避免只说“高级感”。
4. 如果多张风格类似，提炼共同骨架和可变化分支，不为每张图片机械新增一个基因。
5. 明确用户偏好：**最喜欢哪里**，以及**哪些不应照搬**；当用户没说时，Agent 可提出候选，但不能假装用户已确认喜欢。
6. 给出候选基因及适用场景。用户同意后，可以保存原图到本地 Taste Library；公开基因文件只有额外授权才可提交仓库。

学习和本地保存是两个不同动作：**分析不自动等于保存**。

## 四、LIBRARY：积累每位用户独立的视觉 Taste

首选操作是“给用户个人参考图库增加视觉参考”，而不是把用户照片存进公共仓库。详情看 [个人 Taste Library](references/personal-taste-library.md)。

本地 CLI 在技能目录下运行，首次使用需要安装 Pillow：

~~~bash
python -m pip install -r requirements-library.txt
python scripts/taste_library.py add \
  --image "/path/to/reference.jpg" \
  --title "我喜欢的摄影手账风" \
  --genome playful-sky-editorial \
  --tag everyday \
  --like "大粗标题与轻手写字交错" \
  --avoid "原作者品牌标志和虚构日期" \
  --rating 5
~~~

它保存经过元信息清理的图像副本和审美记录到 ~/.poster-genome，不会自动上传网络。支持 list、select、feedback、remove 和 prepare。

**不能把源照片存到公共 skills/poster-genome/ 中。** 本地保存和云端生成是不同的权限；用户授权本地保存不代表可以未经告知把图片发到远程生图服务。

当 Agent 在云端运行、无法访问用户的机器时，需要用户提供图片至 Agent 可访问的工作区，或使用经过用户同意的私有持久化存储。**不能把云端工作区说成用户电脑的本地文件夹。**

公开基因仍在 genomes/，并须符合 schemas/genome.schema.json；新风格先和现有基因比对，不滥增重复类目。未通过测试的基因可保留 draft。

## 五、CREATE：带着真实风格参考图去制作新海报

完整流程见 [参考图驱动创作](references/reference-first-workflow.md) 和 [海报制作](references/creation-playbook.md)。

1. **理解本次素材。** 统计用户源图和每张图中的主体，列出不能改的脸、衣服、照片数量、文本、尺寸。两张宝宝照片必须两个宝宝都出现，除非用户明确允许舍弃一张。
2. **找真正的参考图。** 读取用户本地图库，按风格基因、素材标签、用户 rating 和 liked_for 挑 1–3 张，实际打开图片判断版式关系。优先用户明确指定的参考。
3. **没有参考图就诚实处理。** 默认先问用户是否添加一张喜欢的海报，或允许“无视觉参考的原创尝试”。不能把文字规则冒充真实视觉图。
4. **生成清单，不等于生成海报。** CLI 可以把用户图片、风格参考图片分成不同角色，输出明确的本地文件路径：

~~~bash
python scripts/taste_library.py prepare \
  --source "/path/to/user-photo-a.jpg" \
  --source "/path/to/user-photo-b.jpg" \
  --genome playful-sky-editorial \
  --tag portrait \
  --headline "双宝出行日记" \
  --top 2
~~~

5. **实际把参考图与源图交给图像工具。** 调用支持图像输入的多模态创作/修图工具，把选中的参考图片当成 style reference，把用户源照片当成 content source。只放绝对路径在 Prompt 里**不算**完成输入；确认工具确实能接收它们。用户敏感图片调用远程服务需符合用户权限与服务隐私要求。
6. **分离设计与保真。** 从参考中学习字体、色块、边缘装饰、空间节奏，而不是照搬原作。对人脸、品牌、数字、中文需准确的情形，优先让工具创作背景/图形，再用确定性编辑合成真实照片和文字。不要为了视觉效果重绘用户宝宝的面容。
7. **检查输出。** 核对内容图里所有要求的主体是否出现、文字是否准确、版式是否继承喜欢的视觉特征、没有虚构拍摄参数。若风格达标但缺一个主体，仍然是不合格成品。
8. **反馈提升 Taste。** 用户点评后可提出保留偏好；只有用户同意才能调用 feedback 写入本地库，不能暗中记录。

匹配脚本 scripts/match_genomes.py 仍只能做元数据启发式排序，**不能代替视觉参考检索**。参考图库 CLI 的 select 也不是视觉向量检索：Agent 应实际查看图片后再定风格。

## 六、REFINE：让修改朝用户喜欢的参考靠近

- 同时对照**用户原始素材、用户指定参考图、已生成成品**，优先指出 1–3 处明显缺陷。
- 把错误（错字、人物遗漏、面容失真、虚构数据）和审美差异（字体缺乏动势、元素太死板）分开处理。
- 做定向修改时写清“要借鉴什么 / 不能照搬什么 / 哪些原始内容不得改变”。
- 有图像修改工具就实际修；如果修复需要重新生成而可能损害人脸，优先受控合成。
- 用户没授权保存结果或偏好时，不自行建立私人资料。

## 七、失败分支与边界

- 本地图库为空：询问用户加一张参考或授权无参考原创；不要凭空说“风格来自参考图”。
- 只有 JSON 没有图片：可以提出设计方案，但必须标注是“基于文字基因”，不是图片条件生成。
- 找到参考但宿主不能读取它：不要把文件路径当图片；说明工具限制并请求用户附上图或切换工具。
- 用户要精确保留两个人：不能只生成一个，失败就继续修复或坦白。
- 没有事实来源：不能发明具体日期、温度、摄影机参数、署名、条形码真实含义。
- 私人照片或第三方作品：不默认公开、同步或上传。
- 当前作品已经合适：允许建议保留原样，不强制重新排版。
